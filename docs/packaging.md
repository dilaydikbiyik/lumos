# Packaging Lumos for the stores

The web build is the app. Capacitor wraps `frontend/dist/` in a native shell
so it can do the one thing a PWA cannot do reliably on iOS: receive a push
notification. Everything below assumes `npm run build` already works.

Config lives in [`frontend/capacitor.config.ts`](../frontend/capacitor.config.ts).
Icons are generated by [`brand/generate-app-icons.py`](../brand/generate-app-icons.py).
Listing copy and the store questionnaires are in [store-submission.md](store-submission.md).

---

## What is done, and what needs a machine with Xcode

Done in the repo:

- `capacitor.config.ts`, with the permanent `appId` (`app.lumos.mobile`),
  splash, status bar and push presentation options.
- Every icon and splash size both stores require, generated from `brand/`:
  `brand/generated/ios/`, `brand/generated/android/`, `brand/generated/splash/`.
- Store screenshots at the exact required canvases:
  `STORE=1 LANG_UI=en node demo/capture.mjs` → `demo/screens/en/store/`.
- Public `/privacy` and `/terms`, and in-app account deletion — the three
  things both stores reject an app for not having.

Not done, and **not doable from the repo**, because each needs a paid account
or native tooling:

- `npx cap add ios` / `npx cap add android` — these download platform SDKs and
  generate Xcode/Gradle projects. Run them on a Mac with Xcode installed.
- APNs and FCM credentials. APNs requires the $99 Apple Developer account;
  FCM requires a Firebase project linked to the Play account. Push cannot be
  built or tested before those exist, which is why there is no device-token
  endpoint in the backend yet — it would be code that cannot run.

## First-time setup

```bash
cd frontend
npm install --save @capacitor/core @capacitor/cli @capacitor/ios @capacitor/android
npm install --save @capacitor/push-notifications @capacitor/splash-screen @capacitor/status-bar
npm run build
npx cap add ios
npx cap add android
npx cap sync
```

Then copy the generated art into the native projects:

```bash
python ../brand/generate-app-icons.py
# iOS: drag brand/generated/ios/AppIcon-1024.png into Xcode's asset catalog.
#      Xcode 14+ derives every other size from it.
# Android: copy brand/generated/android/mipmap-*/ into
#      android/app/src/main/res/ — the foreground/background pair is the
#      adaptive icon, ic_launcher.png is the legacy fallback.
```

After any web change: `npm run build && npx cap sync`.

## Deep links

A notification is only useful if tapping it lands on the screen it is about —
"your portfolio dropped" must open `/dashboard`, not the splash.

Both platforms verify ownership of the domain, so this needs the custom domain
to exist first.

**iOS — Universal Links.** Serve `/.well-known/apple-app-site-association`
(no extension, `Content-Type: application/json`) from the domain root:

```json
{
  "applinks": {
    "details": [{
      "appIDs": ["TEAMID.app.lumos.mobile"],
      "components": [{ "/": "/dashboard*" }, { "/": "/recommend*" },
                     { "/": "/explore*" }, { "/": "/holdings*" }]
    }]
  }
}
```

Add the `applinks:<domain>` Associated Domains capability in Xcode.

**Android — App Links.** Serve `/.well-known/assetlinks.json`:

```json
[{
  "relation": ["delegate_permission/common.handle_all_urls"],
  "target": {
    "namespace": "android_app",
    "package_name": "app.lumos.mobile",
    "sha256_cert_fingerprints": ["<from your upload key>"]
  }
}]
```

and an `<intent-filter android:autoVerify="true">` for the domain in
`AndroidManifest.xml`.

Both files must be served by Vercel as static assets with no redirect — a 301
fails verification silently, and the link then opens the browser instead of the
app, which looks like nothing is wrong.

## Push notifications

Blocked on the store accounts. When they exist, the shape is:

1. `PushNotifications.requestPermissions()` on a screen that explains *why*
   first. Asking cold is how you get a permanent denial — and for this app the
   permission is the feature, so it is worth a sentence of context.
2. Register the returned token against the signed-in user (`POST
   /users/me/devices`, a new table keyed on user + token + platform).
3. Send from the backend when the coach has something timely to say. The
   trigger already exists in `behavior_coach`; only the transport is missing.
4. Delete tokens on sign-out and on account deletion — the deletion endpoint
   will need to take the device rows with it, exactly as it takes feedback.

A notification this app sends should never be a nudge to trade. The whole
premise is the opposite: it exists to say *don't*.

## The tracking question

Apple asks whether the app tracks users across apps and websites. The answer
is no, and it must stay no:

- no advertising SDK, no analytics SDK, no IDFA
- Sentry is configured with `send_default_pii=False`
- the only third parties that see anything are listed in the privacy policy

`NSUserTrackingUsageDescription` is therefore deliberately absent from the iOS
config. Adding an analytics SDK later would pull in an IDFA dependency and
turn a "no" into a rejection — check `npx cap sync` output for new transitive
dependencies before each release.
